# 試合記録（#394）の検証記録

`--record-dir` で保存した記録を、公式簡易サーバーの前に置いたプロキシが実際に見た通信と照合した結果です。ハーネスは [`ops/honsen/e2e.py`](../../../ops/honsen/e2e.py) の `--record`、要約は [`runs/`](runs/) にあります。

- 実行環境: macOS arm64、release ビルド、公式簡易サーバー `procon-server-darwin-arm64`
- candidate: `fleet:budget=official:budget_ms=10000`、`--kinds-auto`、1 日 14 秒、5 日
- **Windows では実行していません。**

## 照合した内容

`--record` を付けると、ハーネスは試合後に次を確かめます。1 つでも合わなければ FAIL です。

- 5 つのファイルがすべてあり、どれにもトークンが含まれない
- `setting.json` が `GET /setting` の応答と一致する
- 各日の `plan.actions` が、その日にサーバーへ届いた `POST /` の本文と一致し、全車両ぶんある
- 各日の `day_result` が、サーバーが返した revision と一致する
- `procon record show` が成功する

## 記録 ON / OFF の回答時間

`GET /` を受けてから受理までの秒数（プロキシ側で計測、日ごと）。

| 盤面 | 記録 ON | 記録 OFF |
|---|---|---|
| 16×16 | 0.596 / 0.594 / 0.595 / 0.593 / 0.594 | 0.593 / 0.593 / 0.594 / 0.591 / 0.592 |
| 24×24 | 2.586 / 2.589 / 2.587 / 2.587 / 2.586 | 2.585 / 2.586 / 2.585 / 2.585 / 2.585 |
| 32×32 | 8.487 / 8.003 / 7.989 / 7.994 / 7.990 | 8.281 / 7.997 / 7.997 / 7.995 / 7.995 |

差は 1〜3 ms で、実行ごとのばらつきの範囲です（32×32 の初日は ON / OFF とも他の日より長い）。fleet は与えられた時間を使い切る探索なので、この表は「記録が締切までの余裕を削らない」ことの確認であり、記録処理そのものの時間ではありません。

記録処理そのものは、試合処理のスレッド上で 1 日あたり平均 5 µs、最大 73 µs でした（`cargo test --release -p cli --test match_record_e2e recording_one_day -- --nocapture`、32×32・8 台・交通情報 1024 件）。

## 提出行動の一致

記録 ON / OFF で提出内容が変わらないことは、決定的な `loop` ソルバを使った統合テスト `recording_on_and_off_submit_identical_plans`（`crates/cli/tests/match_record_e2e.rs`）で、5 日ぶんの `POST /` 本文の完全一致として確認しています。fleet は実時間で探索を打ち切るため、同じ設定でも実行ごとに行動列が変わり、この比較には使えません。
