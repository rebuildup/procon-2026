1 日あたりの実計算は **34〜50 ms**（5 日合計 ≈ 0.2 s）。

### コード経路の確認（追加指示 §2）

- `crates/cli/src/coordinator_loop.rs:934-936` — 提出受理後に
  `let diff = state.ends_at - now; sleep(from_secs(diff))` で **`endsAt` まで sleep**。
  60 秒間隔の提出はこの sleep の結果であり、60 秒計算しているわけではない（**確認できた**）。
- `coordinator_loop.rs:1102-1104` `solver_budget_ms` — `endsAt`(秒)×1000 − now − 5000 ms の
  **残り時間**を time-budget 付き solver（`search` 等）に渡す。coverage は決定的貪欲で
  これを使わず 40 ms 台で返す。
- **`endsAt` は i64 の unix 秒**（wire テスト JSON `"endsAt":100`、`×1000` で ms 化）。
  **秒精度しかないため、ミリ秒以下の公式計測時間を wire から復元することはできない**。
  UI の 3.6s はサーバ側時計の値であり、私側ログでの再分解は上記レンジ까が限界。
- 比較対象の混同禁止: **`RunRecord.response_time_us`（offline の decide() 積算＝第 4 軸の
  近似）とも、プロセス全体 elapsed（244 秒 wall、ほぼ sleep）とも別物**。
- 時計の注記: tracing タイムスタンプは **wall UTC**（単調時計ではない）。サーバと本体の
  時計歪みは未測定（上記の一致から小さいと推定）。

### 採点への影響と戦略評価（追加指示 §4、緊急訂正 2026-10-09）

**計測としては正常**（3.6s / 3.9s はログ推定と整合、計測・採点の不一致は無い）。
ただし**戦略的な解釈は次のように訂正する**:

- この競技は **V → D → B → 回答時間の辞書順**。1810 は D=116 vs 135、1811 は
  D=108 vs 120 で**第 2 軸で敗北**しているため、**第 4 軸の速さは順位に一切寄与しない
  無効な優位**。「正常」「強み」として扱わず、改善余地の無いものと解釈しない。
- **coverage は 1 日約 40ms で回答しているのに対し回答期限は 60 秒** — 計算予算の
  ほぼ全量が未使用。**高速回答そのものが悪いのではなく、上位 3 軸で負けているのに
  改善へ使える時間を活用していないことが問題**であり、この余白が改善機会である。
- 比較計測セッションへの依頼（#312 に記録。旧提案「`search` 20s/日で第 3 軸のみ比較」は
  不十分として本訂正で置き換え）:
  1. **第 1 軸・第 2 軸の維持または改善を最優先**に、**全期間スコア（辞書順）で比較する**
  2. 当日の残り時間を使った **anytime 探索**の検証
  3. **複数日ポジショニング**の検証
  4. **玉数改善**の検証（1〜2 軸非劣の下でのみ採用可）
- **新 candidate の arena 投入は、比較計測セッションが offline 検証を終えて SHA と設定を
  引き渡した後のみ**。同一 candidate の安定性確認だけを目的に arena 枠は消費しない。
