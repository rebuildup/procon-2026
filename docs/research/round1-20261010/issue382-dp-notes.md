## 1. 背景と問題

`fleet`（親 candidate #371 / PR #372）は巡回車 1 台ごとに経路の重み（最速 / 均衡 / 省燃料）を 1 つ選び全区間に使う。公式参考 16×16 盤面の初日は 11/12 系列で 1 系列届かない（Issue #382 実測）。PR #386（closed）の区間ごとの重み切り替え（fast / balanced / fuel-lean）では証明に届かなかった。残る方式は「区間ごとに時間と燃料の全パレート経路を使う」厳密探索。

## 2. 定式化

1 日（`day_steps = T`、`fuel_limits = F`）について:

- **移動 1 手**: 六方向のいずれかへ 1 セル。出発セルが時間コスト（平地 2 / 山 3 / 道路 1・2・4 = 交通状態、池は不可）と燃料コスト（平地 1 / 山 2 / 道路 2、池なし）を**両方**負担する（Q10/Q11、`terrain_step_cost` + `fuel_cost`、出発セル課金は Issue #342 P0-C の確定事項）。
- **獲得**: 巡回車がスポットセルに立つと 1 玉（1 エージェント 1 スポット 1 日 1 個の上限、Q15）。系列 = brand。
- **目的**: 3 台の巡回車が集める系列集合の和集合を最大にする。

### 2.1 `mode=legs` — Issue #382 の列挙子の再現

区間（セル対）ごとに (時間, 燃料) パレートフロンティアを label-setting Dijkstra で列挙し、スポット列の DFS を `(最終セル, 系列マスク)` をキーとする支配表（同キー内で (t, f) の非支配集合のみ保持）で剪定する。系列マスクは巡回車ごとに独立なので、割当て段は「マスクの和集合を最大にする」厳密 DP（巡回台数 × マスク集合）。各マスクの到達 (t, f) はパレート集合のまま保持し、勝った割当てに対して `realize_legs`（接尾辞到達可能性 DP）で各区間のラベルを復元、さらに `pareto_path`（フロンティアを逆走する後件探索）で区間の全セル経路を再構成する。

**厳密性**: スポット列計画の全体空間で厳密。区間内の立ち寄り待ち（ウェイト）と給油を抽象化する。スポットセル到達は常に獲得に化ける（在庫 ≥ 1、1 日 1 個上限）と仮定。

### 2.2 `mode=cell` — セル単位ラベル DP

状態 `(セル, 系列マスク, tick) -> 最小燃料`（燃料累計 = 前回の補給からの消費量。タンク = 上限 − 累計 と同値）。遷移は 1 手（出発セル課金）と待ち。給油モデルは 2 種:

- `refuel=on`（緩い）: 到達セルの補給車最短到達時刻 `<= 到達 tick` なら満タンに戻せる（#405 の「区間途中合流」の近似）。**補給車 1 台の供給順は schedule していない**のでチームとしての上界。
- `supply_schedule=q:t[,...]`（厳しい）: 給油は指定セル `q`・時刻 `t` 以降のみ。再生時は補給車自身がそのスケジュールに沿って移動する（時間 Dijkstra 区間 + 合流セルで待機）ので、**再生が通れば実際の 1 台補給ルールで合法**。

**厳密性**: `refuel=off` では 1 台の 1 日の移動計画全体で厳密（待ち・混合重み込み）。給油ありは「1 回の移動は現在のタンクで支払えること」を補給リセットより先に判定する（`apply_due_moves` が課金してから `refill_fuel_if_supply_present` が満タンにする順序に一致。補給セルへの到着移動自体は補給で払い戻されない）。

### 2.3 割当て段

巡回車は互いに独立（交通は日単位の集計で、日内の相殺は scoring に出ない）なので、各巡回車の実現可能系列マスク集合に対し `union |= mask` の DP で和集合最大を厳密に選ぶ。勝った割当てについてスポット在庫の取り合い（同一スポットセルを複数台が拾う）を検出して報告する（今回の勝ちは全例で非重複）。

## 6. その他の検証

- バンドル fixture `medium-16x16`（4 系列 / 32 ステップ / 燃料 64）: `legs` と `cell` が一致（4/4）、再生違法 0。2 モデルの交差検証。
- round1-match3 day 0 を**観測交通**で再生しても 8/10・違法 0（day 0 の道路は平滑寄りで差なし）。
- 実装中に 2 件のバグを修正（いずれも検出は再生系列数 / fuel_short と DP 値の不一致）:
  1. 再生部の plan イテレータが補給車エージェントで先行消費され、1 台分の計画が欠落する。
  2. **給油会計**: DP が補給リセットを支払い判定より先に適用し、タンク 0 での出発（= エンジンでは `FuelShort` 拒否）を許していた。エンジン順序（`apply_due_moves` が課金 → `refill_fuel_if_supply_present` が満タン）に合わせ、`spent + cost <= max_fuel` を先に判定してからリセットするよう修正。修正で §4.3 の目撃がセル 62 から 108 に変わった（他の全結果は不変）。また wire 展開の経路復元をホップ数最小の BFS から時間 Dijkstra に変えた（ホップ最小は時間最短でない: 59→9 は道路経由 5 tick・ホップ最小経由 6 tick）。

## 8. 既知の限界

1. **緩い `refuel=on` はスケジュール不在**: 補給車の存在を「最短到達時刻 <= 到達 tick」で近似し、複数巡回車の需要の競合や供給順を解かない（上界）。合流を特定のセル・時刻に固定する `supply_schedule` で検証する（§4.3 はこの検証済みパス）。
2. **`supply_schedule` の合流点は入力**: DP が合流点を最適化するのではなく、呼び出し側が候補を渡す。単一合流の候補抽出は緩いモデルの目撃から行う。合流が複数箇所に分かれる盤面では、供給順の最適化（#405 `convoy` の本体）がまだ必要。
3. **スポット在庫の競合**: 勝ち割当てで検出・報告するのみ（DP 自体には組み込んでいない）。今回の全勝ち割当ては非重複なので結果への影響なし。
4. **ref-24 / ref-32 未実施**: 16×16 でしか検証していない。
5. **マスク幅**: 系列数 ≤ 64 を `u64` で表現。32×32 の 24 系列まで問題なし。
6. `realize_legs` の復元は「合計が指定の (t,f) に一致するラベル列」を返す。`legs` の支配表が保持する代表 (t,f) と一致するため常に復元できるが、同 (t,f) の複数経路のうち 1 本しか返さない。

## 9. fleet への示唆（統合は別タスク）

- 初日 8 → 9 は**補給合流 1 回**で動くことが `MatchSim` 再生まで含めて証明済み（§4.3、合流 = セル 108・t≤26）。#405 の `convoy`（セル単位 DP + 補給合流 + ロールアウト評価）が本命で、本 DP はその厳密核として再利用できる（1 台 0.1 秒なので日次回答時間 60 秒内に十分）。
- 合流点の設計に 1 つ教訓: 補給セルへの**到着移動自体は補給で払えない**（課金が先）。合流候補は「タンクが尽きるセルの 1 つ手前」に置くのが安全（62 では足りず 108 で足りた）。
- ref-16 の初日 11 → 12 は給油不要の**区間パレート混合**だけで届く（fleet の 3 重み固定が純粋に損をしている盤面）。`legs=pareto`（区間ごとのパレート選択）は #382 の元実装方針どおり有効。
- 一方で round-1 初日 9 には混合重みだけ足りず給油合流が必須。#386 の negative evidence（重み切り替えで届かなかった）と整合する。
