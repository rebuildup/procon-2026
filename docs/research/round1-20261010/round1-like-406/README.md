# 第3試合に似せた難しい盤面での convoy 対 fleet（セッション procon-2026-4f）

## なぜ別の盤面セットが要るか

`honsen-like`（24 盤面、#405）は枠組み（16×16、4 台、5 日、燃料 40）を実戦に合わせているが、スポットを一様に置くので 24 盤面中 22 が D=50 になる。実戦の第3試合盤面は D 44〜46 で、1 回戦の他の試合も 1 位の D が 42〜46 だった。やさしい盤面では D の差が出ないので、実戦に近い難しさの盤面を別に作った。

## 盤面（`boards/`、16 盤面、`gen_round1_like.py`）

- 地形の比率は第3試合盤面の ±0.04（平地 .23、道路 .25、山地 .33、池 .18）、在庫と系列の重複数は第3試合と同じ。
- スポットは外周寄り、開始位置は中央寄りに重み付けして置く。
- 採用条件: 初日に補給車と合流しない場合の種類数の上限が 8 以下（第3試合盤面と同じ値。巡回車ごとのラベル探索で厳密に計算、ソルバには依存しない）。seed 8001 から 2257 盤面引いて、上限 8 が 16、9 が 355、10 が 1886。**採用したのは最も厳しい 0.7% で、平均的な盤面ではない。**
- どの盤面も候補の設計・調整には使っていない。

## 結果 1: 自チームの交通だけ（`own-roads.runs.jsonl`、`procon-eval`、`3d30381`、seed 42、kinds `S,P,P,P`）

16 盤面 + 第3試合盤面。基準は `fleet:budget=official:iters=60000:chains=4`。

| 候補 | 勝 / 負 | D が下がった盤面 | D 合計 | B 合計 | 1 日の最大 |
|---|---|---:|---:|---:|---:|
| `fleet` | — | — | 796 | 1150 | 3.0 秒 |
| `convoy`（既定） | 16 / 1 | 0 | 811 | 1248 | 7.0 秒 |
| `convoy:depth=2` | 15 / 2 | 0 | 812 | 1231 | 4.7 秒 |
| `convoy:depth=1` | 14 / 1 | 1 | 806 | 1243 | 4.2 秒 |
| `convoy:width=48` | 17 / 0 | 0 | 811 | 1247 | 10.9 秒 |
| `convoy:forecast=persist` | 17 / 0 | 0 | 813 | 1284 | 5.4 秒 |

この条件では他チームの交通がないので、「今日の道路が続く」予測（persist）が当たる。persist が良く見えるのはそのため。

## 結果 2: 合成した混雑つき（`synthetic-traffic.jsonl`、`round1_rollout traffic=observed`、`421` ブランチのバイナリ、convoy のコードは `3d30381` と同じ）

各盤面に 2 通りの混雑（`traffic/`）を与えた 32 試合。混雑の量は実戦 run の日別の割合に合わせた（1 日目から順に 混雑 0 / 9 / 37 / 22 / 26%、渋滞 0 / 0 / 8 / 6 / 6%）。どの道路が混むかは道路ごとの固定の人気度 7 割＋日ごとの乱数 3 割で決めた合成で、実際の他チームの動きではない。

| 候補 | 勝 / 負 | D が下がった試合 | D 合計 | B 合計 | 1 日の最大 |
|---|---|---:|---:|---:|---:|
| `fleet` | — | — | 1485 | 2092 | 2.2 秒 |
| `convoy`（既定 = `forecast=both`） | 30 / 2 | 0 | 1521 | 2303 | 4.7 秒 |
| `convoy:forecast=persist` | 30 / 2 | 2 | 1519 | 2356 | 4.0 秒 |
| `convoy:forecast=busy` | 30 / 2 | 0 | 1518 | 2290 | 3.0 秒 |

- 既定の `convoy` は 1 試合あたり D +1.1、B +10%。負けの 2 試合は同じ盤面（s9018）で、V・D 同点の B −1。
- 違法・燃料不足・拒否は全候補で 0。
- 混雑があると `forecast=persist` は 2 試合で D を落とす。既定の `both` は D を落とした試合が 0 で D 合計も最大。`both` を変える理由はない。

再集計: `python3 tab.py own-roads.runs.jsonl`。

## convoy は D の上限にどれだけ近いか（`caps2.py`、`day-caps.jsonl`）

混雑つき 16 試合（各盤面の 1 通り目）で、`convoy` が実際に通った各日の開始状態から当日の種類数の上限を厳密に出した（`origin/421` のバイナリ、`CONVOY_DEBUG=1` で候補集合の最大値も記録）。

| 1 試合（5 日）あたりの平均 | D |
|---|---:|
| `convoy` が選んだ計画 | 47.56 |
| その日の候補集合の中の最大 | 47.62 |
| 上限: 1 台だけ補給車に合流・同行、他は手持ち燃料（実現可能） | 47.75 |
| 上界: 全車が独立に合流できると仮定 | 47.88 |
| 補給なし | 46.19 |

当日だけを見た上限との差は 1 試合あたり 0.2〜0.3。この盤面群では、補給 1 台・巡回 3 台の構成で `convoy` の D はほぼ上限にある。80 日のうち上限に届かなかったのは 4 日（初日 7 対 8 が 1、中日 8 対 9 が 2、9 対 10 が 1）。

最終日の玉数（`bcap.py`）: 16 試合の合計 274 に対し、巡回車ごとの「立てるスポット数」の和で作った上界は 317。ただしこの上界は在庫の取り合い（16 スポット中 9 が在庫 1）と種類数の維持を無視しており、実際に `convoy` が上界を超えた盤面もある（2 台に給油したため）。在庫を入れた厳密な上限は出していない。

## 補給車をどのスロットに置くか（`slot/`）— 効果なし

`boards/` の 16 盤面では、補給車のスロットを変えると `convoy` の D 合計が 811（スロット 0）から 816〜817（スロット 2 / 3）に上がり、盤面ごとに最良を選ぶと 820 になった（`slot/tight-*.runs.jsonl`）。ただしこの 16 盤面は「スロット 0 が補給車のとき初日が厳しい」ことで選んでいるので、他のスロットが良く見えるのは選び方の偏りの可能性がある。

偏りのない条件で測り直した。`slot/gen_sym.py` は「誰を補給車にしても、残り 3 台が補給なしで初日に届く種類数が 9 以下」の盤面だけを採る（24 盤面、`slot/boards/`、各盤面の `.caps` にスロット別の初日上限）。

| 補給車のスロット | D 合計（24 盤面） | B 合計 |
|---|---:|---:|
| 0（現行） | 1172 | 1958 |
| 1 | 1173 | 1954 |
| 2 | 1172 | 1972 |
| 3 | 1170 | 1931 |
| 盤面ごとに最良（後知恵） | 1173 | 1995 |
| 初日の上限が最大のスロットを選ぶ規則 | 1172 | 1959 |
| `fleet iters=8000` の試走で選ぶ規則 | 1173 | 1951 |

D はスロットによらずほぼ同じ（24 盤面中 22 が 49 = 初日 9 + 残り 4 日 10 の上限）。後知恵で最良を選んでも D +1、B +1.9% で、事前に選ぶ 2 つの規則はどちらもそれに届かない。実戦の第3試合盤面でも、初日の上限はスロット 0 が最良タイ（補給なし 8 / 1 台同行 9）。スロットの探索は採らない。
