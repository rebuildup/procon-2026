# Issue #275 — 提案の hex 表現を実装へ合流

基準は `docs/design/proposals/design-system.html`。Family A/B/C の先頭12記号ずつを `scripts/extract-viewer-marks.py` で抽出し、形状・fill・stroke・opacity を保持する。A は既存 role key、B/C は peak-/terrace- 接頭辞。描画シーンは family を引数で選択でき、既定は A。操作 UI と提案 HTML は変更しない。`viewer-icons.json` は UI 用 Octicons のため変更しない。

以前の単色マスクでは canonical の keyline と内部線が失われていた。共有 RGBA アトラスで元の色と線を保持し、白 halo を追加する。GPU と Canvas は同じアトラスを描画する。hex 背景は dot / hatch / wave / dash のテクスチャと ink keyline + white halo に変更する。

色の例外: Primer data-vis を基準とする既存 palette API を維持しつつ、hex と記号の最終色は Issue の優先規則に従い提案の公式図実測値を使用する。plain #8ed973、mountain #bfbfbf、water #46b1e1、road #156082。系列 s0–s5 は #cc9900 / #c04f15 / #b03a55 / #7048a8 / #0f7f96 / #2f7d4f。patrol #00b050、supply #e59edd。UI token の独自定義は追加しない。

検証: canonical 36記号の抽出一致、全 family の GPU 描画、15px の隣接系列標本、Solvers/Live スクショ・録画、GPU 不可時 Canvas、frontend gates を確認する。

## 共通構造からの再実装

前版は単独glyphだけの抽出とGPU/Canvas別々のtexture解釈だったため、見た目の一致を保証できていなかった。今回は `viewer-structure.json` に canonical `.hexfield` の defs / patterns / inherited group attributes / hex layers / series layers / original centers を抽出する。`scripts/extract-viewer-marks.py --check` はこの全構造も検証する。

`hex-assets.ts` がこの構造を組み立て、ブラウザのSVG rasterizerで一度だけ共有アトラスへ変換する。SVGを地図のDOMに置かない。GPUとCanvasには同じ完成済みhexを渡し、procedural shader / Path2D interpreter / 後付けhaloを撤去した。Family Aの6系列はfieldにある実際の記号と二重境界を使う。その他のfamily / agent / legendは単独標本のnative SVG形状を使い、提案にないhaloを追加しない。

Sceneの占有はcell indexで明示する。地形記号と系列記号の重複描画を撤去。sceneはreadonlyで、compositionをWeakMapでcacheする。GPUは1つのpipeline・1 pass・1 instanced draw、atlasはdeviceごとに初期uploadだけ。camera操作時は32byte uniformのみを更新し、instance bufferを再転送しない。buffer capacityは固定48件から必要に応じて増加する方式に変更した。

追加検証: canonical SVG / GPU / Canvasの同座標比較（平均channel差を記録）。camera60回のatlas/instance再転送不在を検証。6hex基準と48cell demoのCPU submission p95を測定する。GPU throughputや実機FPSの保証とは区別する。

最終実装 `0f61b76`。アトラス境界の余白は元の白halo全体が収まる68unitとして明示した。frontend check / lint / format / unit10件 / build 成功。元SVG/GPU/Canvasの同座標画素比較とcamera60回のinstance/atlas再転送不在を確認。平均channel差（0–255尺度）はGPU対Canvas約0.12、GPU対元SVG約0.68。48cell demoのCPU submission p95は約0.1ms。計測の条件と数値はrenderer-performance.jsonへ保存する。
