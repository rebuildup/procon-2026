# ヘキサうどん 戦略ノート（並走トラック独自分析）

この文書は、本並走トラックが独自に組み立てた戦略の叩き台です。
主導トラック側の戦略メモ（CONFIDENTIAL 扱い）とは独立に、公開資料のみから再構成しています。

## 1. 勝ち筋の優先順位（公式ルールから）

判定基準は降順で重要:

1. **うどんの種類数**（系列の異なり数）
2. **各日の種類数の累積**（毎日できるだけ多種類）
3. **うどんの総玉数**
4. **各日の最終回答時刻の累積**（早いほど有利）

→ 1日目で2系列だけ全玉取れても、2日目に1系列も取れないと累積種類数で負ける。
「全日まんべんなく多系列を触る」が最優先で、総玉数は最後の追い要素。

## 2. 系列と在庫の読み解き

- 系列数 ≤ スポット数、スポット数 ≥ エージェント数
- 各スポットの最大在庫 = 1チームのエージェント数
- 1日1スポット1玉ずつしか取れない
- スポットの在庫はチーム独立 → 相手チームが全部取っても自チームのスポットは満タン

含意:
- **1チームが1日に1系列から取れる最大玉 = エージェント数（ただし巡回車の数）**
- 系列数が多いマップでは、巡回車を系列ごとに1台ずつ配置するのが理想
- 巡回車が3体なら「1系列だけ集中的」より「3系列を1日1玉ずつ」の方が強い
- エージェント数の上限 8 に対して系列数が同程度なら、巡回車を全種類に展開できる

## 3. 補給車・巡回車の役割分担

### 3.1 燃料経済の制約
- 巡回車: 燃料上限 = `1日目のステップ数 × 1〜3`
- 補給車: 燃料制限なし、燃料を消費せずに移動可能

つまり補給車は「タンクローリー」として巡回車に追随すればよく、
**巡回車の単独行動範囲 = 燃料上限 / 消費率** で決まる。

### 3.2 1台の巡回車が1日に動ける平地段数
- 上限が `daySteps × 2` 程度、平地中心なら最大 `daySteps × 2` セル
- 山地中心なら最大 `daySteps × 1.5` セル
- 道路（順調）なら最大 `daySteps × 4` セル

→ マップの片側を巡回するだけで燃料を使い切る可能性あり。
**長距離は道路メイン、寄り道は平地、というルート設計** が基本。

### 3.3 巡回車と補給車の結合パターン
大きく3パターン:

| パターン | メリット | デメリット |
|---|---|---|
| **同位置・同行動** | 補給切れを起こさない | 補給車が「遊休」 |
| **巡回車が先行・補給車が後追いで先回りに配置** | 補給車の自由度が高い | 合流タイミングの設計が必要 |
| **複数ペアに分割** | 並列に系列を巡回 | ペア間の連携が複雑 |

## 4. 道路渋滞のゲーム理論的性質

- 道路の移動ステップは状態（順調1/混雑2/渋滞4）で変動
- 状態は前日・前々日の交通量から決まる（全チーム合算）
- 閾値: 混雑基準 1〜5、渋滞基準 2〜10

→ 道路を共有する **N チーム** が同じ道を使うと、状態が悪化する。
**早い者勝ち**だが、過剰に混雑した道路は次の日さらに遅くなる。
「ナッシュ均衡」的には、各チームが分散して使うのが合理的。
逆に「誰も使わない道路」 = 翌日 fastest route として再利用可能。

### 含意
- **初日に全力で1本の道路を集中利用 → 2日目にその道路が渋滞化** という罠
- **分散ルート**を各チームが採用するのが自然だが、
  本選では「相手より先に混雑を予測して空いている道を確保」が勝負
- 渋滞閾値が小さい（2〜3）なら、交通量の影響が大きく戦略性が上がる

## 5. アルゴリズム設計の方針

### 5.1 入力制約
- マップ最大 32×32 = 1024 セル
- スポット数 ≤ 32、最大系列数 = スポット数
- エージェント 3〜8体
- 1日 200 ステップ程度（32×4 = 128 〜 32+32 = 64 から推定）
- 1日 1分（daySeconds ≈ 60）

### 5.2 リアルタイム要件
1分以内に全エージェントの `daySteps` 個の行動を出力する必要がある。
→ 1ステップあたりに使える計算時間 = 60秒 / daySteps = 数ms 〜 数十ms。

### 5.3 段階的なアルゴリズム案

**Phase 1（短期・予選）: 貪欲法**
- 各ステップで「最も近い未取得スポット」「最も近い巡回車」などヒューリスティック
- ルックバック不要、即時計算可能
- 系列数を最大化するのが主目的

**Phase 2（中期・本選前）: 軽量な経路探索**
- 各スポット間の最短路を A* で前計算
- スポットを系列クラスタリング → 各クラスタにエージェント1台割当
- 巡回車の燃料残量と歩数を管理

**Phase 3（理想）: 集中計算 + 部分MCTS or ILP**
- 全日を見通す必要があるので daySeconds 内にソルバーを回す
- WGSL / GPU 並列化で盤面の最短路を一括計算
- 状態空間は `step × agent × pos` ≈ 数百 × 8 × 1024 = 数百万

### 5.4 並列化ポイント
- A* のゴール固定での複数スタート並列化 → WebGPU compute shader
- スポット系列のクラスタリング（Union-Find 等） → CPU 軽量
- 行動計画ソルバーのサンプリング → GPU モンテカルロ

## 6. 設計上の未確定事項

以下は **実装着手前に** 決める必要あり:

1. **行動計画をターン単位で先読みするか日単位で一括提出か**
   - 公式「回答は日単位提出」と読めるが、Q&A で再提出可否を確認すべき
2. **複数日の計画をまとめて解くにせよ、1日ごとに分けて解くにせよ**
   - 分割した方が応答性良い、統合した方が最適
3. **交通量予測のモデル化**
   - 相手チームの戦略が不明 → ベイズ推定 or 楽観的（最良状態）前提
4. **スポット系列の事前クラスタリング vs 動的計画**
   - 1日目は静的に決め打ち、2日目以降は動的に再編
